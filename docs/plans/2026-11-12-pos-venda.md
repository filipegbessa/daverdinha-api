# Pós-venda — plano de implementação (API + site)

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** depois de pagar (ou se inscrever de graça), o comprador vê na hora que deu certo, recebe a confirmação por e-mail e consegue voltar aos pedidos e ingressos quando quiser, sem criar conta. Cada participante tem um ingresso com QR code, lido na entrada pelo admin.

Um plano só pros dois repositórios: as tarefas de API ficam aqui (`daverdinha-api`), as do site citam os caminhos do `daverdinha`. Os contratos abaixo são a fonte da verdade pros dois.

## Onde estamos (2026-11-12)

- **Confirmação na tela:** existe. O Pagar.me devolve o comprador pra `/pedido/<token>` (`success_url`). A página lê o pedido na API, que consulta o Pagar.me quando o pedido ainda está pendente (no máximo uma vez por minuto) e aplica o webhook quando ele chega. Pago, a página mostra "Pedido confirmado!", "Ingresso confirmado!" ou "Inscrição confirmada!".
- **Buraco 1:** se o comprador volta antes de o pagamento ser processado (Pix, ou o webhook atrasado), a página mostra "Aguardando pagamento" e só atualiza se ele clicar em "Já paguei".
- **Buraco 2:** nenhuma mensagem sai. O único acesso ao pedido é o link `/pedido/<token>`; quem fecha a aba perde o pedido.
- **Buraco 3:** o ingresso é a página do pedido com os nomes. Não tem QR, e o check-in no admin é pelo nome.

## Decisões já tomadas

| # | Decisão |
|---|---|
| 1 | **Confirmação só por e-mail** (decidido em 2026-11-12), pelo **Resend** (grátis até 3.000 e-mails por mês e 100 por dia). Sem WhatsApp por enquanto. |
| 2 | **Sem conta nem senha.** O acesso é sempre por link: o do e-mail de confirmação ou um link novo pedido em "Meus pedidos", que chega no e-mail do comprador. |
| 3 | **QR code por participante, já nesta etapa** (decidido em 2026-11-12). O QR carrega só um código aleatório do ingresso, nada pessoal. No admin, a lista de presença ganha um leitor pela câmera do celular; o check-in pelo nome continua. |
| 4 | **E-mail nunca derruba o pagamento.** Falha no envio vira log e fica marcada pra reenvio; o pedido continua pago. Cada pedido recebe uma confirmação só, mesmo com o webhook repetido. |
| 5 | **"Meus pedidos" não revela nada na tela.** Quem digita um e-mail sempre vê "Se houver pedidos nesse e-mail, mandamos os links"; a lista só chega na caixa do dono. |
| 6 | **Remetente único `Daverdinha <contato@daverdinha.com.br>`** (2026-11-12): a cliente só tem essa conta. Envia e recebe as respostas pelo mesmo endereço (`EMAIL_FROM` e `EMAIL_REPLY_TO` iguais). O Resend só precisa do domínio verificado; a caixa de entrada continua onde está. |
| 7 | **Nada de dados de pagamento no nosso e-mail** (2026-11-12): o recibo do pagamento (forma, parcelas, autorização) é do Pagar.me. O nosso fala do pedido: o que foi comprado, entrega ou retirada, os ingressos com QR e o link. Conferir no sandbox que o Pagar.me manda mesmo o recibo ao comprador; se não mandar, o total pago entra no nosso. |

**Dá pra implementar tudo sem a chave do Resend:** sem `RESEND_API_KEY` o envio só vira log (Tarefa 1), e os testes usam um cliente falso. A chave e o DNS só são necessários na Tarefa 8.

## Contratos

```ts
// SiteOrderTicket ganha:
//   code: string   // único, aleatório, ~10 caracteres sem ambiguidade (sem 0/O, 1/I), ex. "K7Q2-M9XP"
//                  // é o conteúdo do QR; o número do pedido é sequencial e não serve

// SiteOrder ganha:
//   confirmationSentAt: DateTime | null   // idempotência do e-mail (decisão 4)

// PublicSiteOrder.tickets passa a ter o código:
//   tickets: { attendeeName: string; unitPrice: number; code: string; checkedIn: boolean }[]

// POST /checkout/orders/lookup  (público)  { email }
//   202 sempre, com o mesmo corpo; se houver pedidos pagos ou pendentes desse e-mail nos últimos 12 meses,
//   manda um e-mail com o link de cada um. Limite: 3 pedidos por e-mail e 20 por IP a cada hora (429 depois).

// POST /site-order-tickets/check-in-by-code  (ClerkAuthGuard)  { eventId, code }
//   200 -> Attendee (o mesmo da lista de presença) com checkedInAt
//   404 -> código desconhecido
//   409 -> { reason: 'other_event' | 'not_paid' | 'already_checked_in', checkedInAt? }
```
